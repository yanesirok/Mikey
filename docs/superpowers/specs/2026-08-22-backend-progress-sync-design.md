# Бэкенд: аккаунт и синхронизация прогресса

Дата: 2026-08-22. Статус: дизайн утверждён, инфраструктура развёрнута, реализация не начата.

## Задача

Сегодня всё, что знает приложение о пользователе, живёт в `PlayerPrefs` и умирает
вместе с переустановкой. Нужно три вещи, названные владельцем продукта:

1. не терять прогресс при переустановке и смене телефона;
2. аккаунт со входом через Google;
3. возможность смотреть данные пользователей у себя.

Третье закрывается дашбордом Supabase без единой строки кода, поэтому строим первое
и второе.

## Что хранится локально сегодня

Это же — черновик схемы. Ключи `PlayerPrefs`:

| Ключ | Поля | Семантика |
|---|---|---|
| `Mikey.Profile.UserData` | `DisplayName`, `Gender`, `Age`, `WeightKg`, `HeightCm` | валидация: возраст 10–100, вес 30–300 кг, рост 100–250 см (`ProfileUserDataValidation`) |
| `level0.results` | `PushUpReps`, `SquatReps`, `YokoGeriSlowReps`, `YokoGeriBestZone`, `WallSitSeconds`, `YokoGeriHoldSeconds` | max-merge: слабый повтор не понижает результат |
| `level1.progress` | список `{Id, CleanReps}` по техникам | max-merge |
| прогрессия | `TutorialProgressState` | монотонное перечисление |
| звук | громкости музыки / эффектов / голоса | настройка устройства |

## Решения

### Supabase, а не Firebase и не свой сервер

Postgres со встроенным входом через Google. Клиент ходит обычным HTTPS/JSON через
`UnityWebRequest`, без тяжёлого SDK — APK и так 97 МБ, и Firebase Unity SDK с Play
Services прибавил бы заметно. Max-merge на Postgres пишется как `GREATEST` в одну
строку, а не транзакциями вручную поверх документной базы. Аналитика «сколько людей
дошло до уровня 1» — обычный `GROUP BY`, без выгрузки в третий сервис. Свой сервер
отвергнут как втрое большая работа и постоянный хвост из хостинга, деплоя, бэкапов и
ротации ключей.

### Локальное хранилище остаётся главным

`PlayerPrefs` не заменяется, а становится кэшем. Игра обязана полностью работать без
сети: люди тренируются где угодно, и падение связи не должно ронять тренировку. Вход
в аккаунт **необязателен** — без него приложение ведёт себя ровно как сейчас, просто
без резервной копии.

### Одна функция вместо набора запросов

`sync_progress(payload jsonb) returns jsonb`: принимает состояние устройства, сливает
с серверным в одной транзакции, возвращает слитый результат, клиент пишет его обратно
в `PlayerPrefs`. Один round-trip, атомарно, без диалогов «какую версию оставить».
Отдельными REST-апдейтами слияние разъедется между таблицами, а доверять его клиенту
нельзя.

### Два разных правила слияния

Смешать их в одно — самая вероятная ошибка в такой задаче, поэтому разведены явно:

| Данные | Правило | Почему |
|---|---|---|
| Результаты уровней 0/1, состояние туториала | max-merge, `GREATEST` | уже так устроено локально; конфликтов не бывает по построению |
| Имя, пол, возраст, вес, рост | последняя запись побеждает, по `profile_updated_at` | максимум здесь бессмыслен: смена веса — правка, а не рекорд |

### Личность клиент не сообщает

`sync_progress` помечена `security definer` и берёт `auth.uid()` из токена. Поверх —
Row Level Security на всех таблицах: правило «вижу только свою строку» живёт в базе, а
не в проверках кода, которые забываются. Границы валидации продублированы
`CHECK`-ограничениями — клиенту верить нельзя, даже своему.

### Что не синхронизируем, намеренно

- **Громкости звука** — настройка конкретного устройства, тащить её на другой телефон вредно.
- **CSV с координатами скелета** (`PoseController.SaveRecording`) — это биометрия, по
  сути запись тела. Отладочный файл на устройстве и хранение на сервере — разные классы
  обязательств. Остаются локальными.

## Схема

Три таблицы, все через `on delete cascade` на `auth.users` — удаление аккаунта вычищает
всё само.

```
profiles          id uuid PK -> auth.users, display_name, gender,
                  age int CHECK 10..100, weight_kg real CHECK 30..300,
                  height_cm int CHECK 100..250,
                  tutorial_progress int,
                  profile_updated_at timestamptz   -- решает, чья правка новее

level0_results    user_id uuid PK -> auth.users,
                  pushup_reps, squat_reps, yokogeri_slow_reps,
                  yokogeri_best_zone, wallsit_seconds, yokogeri_hold_seconds

level1_progress   PK (user_id, technique_id), clean_reps
```

`technique_id` — свободный текст без справочника в базе. Каталог упражнений устроен
так, что добавление техники — один вызов `ExerciseCatalog.Register`; требовать ради
этого миграцию базы не стоит. Строка на технику, а не JSON-колонка: тогда «сколько
людей освоило mae geri» — обычный `GROUP BY`.

Функции: `sync_progress(payload jsonb)` и `delete_account()`.

## Вход

Нативный Google Sign-In в новом `MikeyAuth.androidlib` (Credential Manager) отдаёт
ID-токен, Unity меняет его в Supabase на пару access/refresh.

Refresh-токен идёт в `EncryptedSharedPreferences`, **не** в `PlayerPrefs`: последний на
Android — обычный XML, который вдобавок попадает в автоматический бэкап Android.
Долгоживущий ключ от аккаунта лежал бы там открытым текстом и уезжал в облако вместе с
бэкапом.

Publishable-ключ Supabase зашивается в APK — так и задумано, это публичный ключ. Данные
защищает RLS, а не его секретность.

## Клиент

Новая сборка `Mikey.Backend` в `Assets/Backend/` — отдельный asmdef, как у `Mikey.Pose`
и `Mikey.UI.*`; сеть не должна протекать в игровые сборки.

| Компонент | Что делает |
|---|---|
| `SupabaseConfig` | ScriptableObject: URL и publishable-ключ. Не константы — dev и prod это разные ассеты |
| `SyncPayload` | **Чистый C#, без UnityEngine.** Собирает запрос из хранилищ, применяет слитый ответ |
| `SupabaseSession` | Токены и обновление до истечения |
| `ITokenStore` | `AndroidTokenStore` (EncryptedSharedPreferences), `MemoryTokenStore` для редактора и тестов |
| `IAuthGateway` | `AndroidGoogleAuth` через Credential Manager; в редакторе заглушка «недоступно» |
| `SyncService` | MonoBehaviour на GameObject `UI`, где живёт всё остальное |
| `MikeyAuth.androidlib` | Android-плагин рядом с `MikeyPose.androidlib` |

Два интерфейса с двумя реализациями — не абстракция впрок: в редакторе
EncryptedSharedPreferences физически нет, а тестам нужна подмена. Этот приём в проекте
уже применён — `IAudioSettingsStorage` и `ITutorialProgressStorage` устроены так же,
вплоть до `FakeTutorialProgressStorage`. `SyncPayload` свободен от UnityEngine по той же
причине, что `PracticeSessionModel` и `TutorialProgressPresenter`.

## Когда синхронизировать

Триггеров намеренно мало, ни один не блокирует интерфейс:

- после успешного входа — подтянуть, что уже есть на сервере;
- на `OnApplicationPause(true)` — надёжный момент «пользователь ушёл» на Android;
- сразу после записи подхода в `Level0Results` или `Level1Progress`.

Никаких таймеров и синхронизации по кадру. Одновременно летит не больше одного запроса;
изменение во время полёта ставит флаг и вызывает повтор после.

## Ошибки

Правило: локальные данные потерять нельзя.

- **Нет сети, таймаут, 5xx** — no-op, локальное состояние нетронуто, повтор при следующем
  триггере. Сообщения пользователю нет: неудавшийся бэкап — не игровое событие, и дёргать
  им человека посреди тренировки незачем.
- **401** — обновляем токен; не вышло — считаемся разлогиненными, локальные данные на месте.
- **4xx на валидации** — лог и остановка. Повтор отклонённого запроса по кругу — разряженная
  батарея, а не надёжность.
- Обратная запись применяет только слитый ответ, который для прогресса по построению не
  меньше локального.

## Приватность и удаление аккаунта

Возраст, пол, вес и рост — персональные данные, а нижняя граница возраста 10 лет означает
несовершеннолетних пользователей. Отсюда:

- вход необязателен, приложение полностью работоспособно без него;
- перед первой отправкой — экран согласия с перечнем того, что уходит на сервер;
- «Удалить аккаунт» на экране Profile: `delete_account()` сносит пользователя, каскад
  уносит все три таблицы, клиент чистит сессию. **Локальный прогресс на устройстве
  остаётся** — он оттуда и не уезжал, а телефон принадлежит человеку. Это сказано прямо в
  тексте подтверждения, чтобы «удалено» не значило одно на словах и другое на деле.

Кнопка входа — на экране Profile: он уже владеет данными пользователя. Это правка
`MikeyApp.uxml`.

## Тесты

- `SyncPayloadTests` — сборка запроса, применение ответа и главный случай: **неудачный или
  частичный ответ никогда не понижает локальное значение**.
- `SupabaseSessionTests` — арифметика истечения, обновление заранее, сброс сессии при
  провале обновления.
- `supabase/tests/sync_progress.sql` — простые `assert`-блоки: максимум берёт большее,
  профиль берёт более свежий `profile_updated_at`, RLS не пускает к чужой строке.

Интеграционного теста против живого Supabase не будет: он требует секретов в CI и падает
от сети.
