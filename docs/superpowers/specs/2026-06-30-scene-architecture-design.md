# Архитектура сцен: гибридная модель (постоянная UI-сцена + аддитивные тяжёлые сцены)

**Дата:** 2026-06-30
**Статус:** одобрено к реализации (дизайн)
**Тема:** переход от одной сцены со всеми экранами к гибридной модели в связи с добавлением 3D-анимаций, видео и эффектов.

## Контекст и проблема

Сейчас весь фронтенд живёт в одной сцене `Assets/Scenes/SampleScene.unity`:

- Один `UIDocument` рендерит `Assets/UI/MikeyApp.uxml` — монолит на 893 строки с 10 экранами
  (`title`, `intro`, `menu`/Home, `combineIntro`, `camTest`, `combine`, `techniques`,
  `practice`, `map`, `profile`).
- `ScreenManager` показывает один экран за раз, переключая `display: none/flex` у элементов
  с классом `.screen`. Навигация — по конвенции `go-<screenId>`.
- Контроллеры `CombineScreenController`, `CameraTestController`, `PracticeController` и
  `SafeAreaController` висят на одном GameObject `UI` рядом с `UIDocument`.
- Экраны общаются через интерфейс `IScreenNavigator` (событие `ScreenChanged`, `Show`,
  `CurrentScreen`).

Для чисто-UI приложения одна сцена — идиоматичный и правильный выбор. Но в проект скоро
добавляются **3D-модели и анимации, фото, видео и эффекты**. При этом подходе все тяжёлые
ассеты всех экранов окажутся в памяти одновременно, монолитные файлы (`.unity` и `.uxml`)
породят постоянные merge-конфликты, а разделить нагрузку по экранам будет нечем.

### Тяжёлые vs лёгкие экраны

- **Тяжёлые** (3D/видео/эффекты/камера): `title`, `intro`, `camTest`, `practice`, `map`.
- **Лёгкие** (данные/списки/дашборды): `menu` (Home), `combineIntro`, `combine`,
  `techniques`, `profile`.

Примерно 50/50 — отсюда выбор гибрида, а не «всё в одной» или «сцена на каждый экран».

## Рассмотренные подходы

### A — Оставить одну сцену
3D прятать за UI-панелями через overlay-камеры / RenderTexture.
- ➕ Мгновенные переходы, общий стейт тривиален, ничего не ломается.
- ➖ Все тяжёлые ассеты в памяти одновременно; гигантские `.unity`/`.uxml` → merge-ад;
  память не выгрузить. Ломается ровно из-за планов на 3D/видео. **Отклонено.**

### B — Сцена на каждый экран (`LoadScene(Single)`)
- ➕ Максимальная изоляция, мелкие файлы, в памяти один экран.
- ➖ Задержка загрузки на каждом переходе (даже Home→Profile); дёрганый нижний таб-бар;
  общий стейт через `DontDestroyOnLoad`/синглтоны; выбрасывается весь оттестированный
  `ScreenManager`/`IScreenNavigator`; большой переписыватель. **Отклонено.**

### C — Гибрид (выбрано) ⭐
Постоянная UI-сцена + аддитивные тяжёлые сцены, общий стейт через ScriptableObject,
инкрементальная миграция. Закрывает все пять мотиваций: размер файлов, память,
«правильность», merge-конфликты, полноценные сцены под 3D/видео/эффекты.

## Целевая архитектура

### Сцены

- **`Assets/Scenes/App.unity`** — постоянная сцена-бутстрап, всегда загружена (индекс 0 в
  Build Settings). Содержит:
  - общий `UIDocument` (UI Toolkit для всех лёгких экранов **и** HUD-оверлеев тяжёлых);
  - `ScreenManager` (роутер), `SafeAreaController`;
  - `SceneLoader` (аддитивная загрузка/выгрузка);
  - `AudioListener`;
  - ссылки на ScriptableObject-стейт.
- **`Assets/Scenes/Screens/{Title,Intro,CameraTest,Practice,Map}.unity`** — тяжёлые
  аддитивные сцены. Каждая со своей камерой (URP camera stacking — проект на URP), светом,
  3D-контентом, Timeline, VideoPlayer, эффектами и небольшим per-scene контроллером.

Лёгкие экраны (`menu`, `combineIntro`, `combine`, `techniques`, `profile`) остаются
UI-панелями в общем документе и переключаются мгновенно, как сейчас.

### Навигация (ядро)

`ScreenManager` становится роутером с двумя типами назначений:

- **Panel** (лёгкий) → переключение `display` в общем `UIDocument` (текущее поведение).
- **Scene** (тяжёлый) → `SceneLoader.LoadAsync(sceneName)` аддитивно + выгрузка предыдущей
  активной тяжёлой сцены.

Реестр сопоставляет `screenId → тип назначения` (`ScreenRoute`). Конвенция
`go-<screenId>` сохраняется: обработчик клика спрашивает роутер, тот решает panel-toggle
или scene-load. **`IScreenNavigator` остаётся неизменным публичным контрактом** — существующие
контроллеры не знают и не зависят от типа цели.

**Ключевая тонкость, снижающая риск миграции:** HUD-разметка `camTest` и `practice`
(счётчик повторов, cue-pill, кнопки действий) **остаётся в общем `UIDocument`**; в аддитивную
сцену уезжает только 3D/камера/видео *за* HUD. Благодаря этому `CameraTestController` и
`PracticeController` продолжают биндиться к общему root, а их существующие тесты остаются
зелёными. 3D-сцена рендерится под UI-панелью через порядок сортировки PanelSettings / стек
URP-камер.

### Общий стейт

ScriptableObject-ассеты, ссылающиеся из контроллеров и App-сцены, и из тяжёлых сцен:

- `PlayerProfileState` — пояс, уровень, стрик, монеты, атрибуты STR/SPD/AGI/END.
- `ProgressionState` — пройденные города, текущий урок/элемент.

Это ассеты, а не объекты сцены — переживают загрузки сцен естественно, без
`DontDestroyOnLoad`. Заменяют захардкоженные мок-значения в UXML.

**YAGNI:** на первом срезе заводим только тот стейт, который реально читает/пишет первый
перенесённый экран. Остальные поля добавляются по мере переноса экранов.

### Жизненный цикл загрузки (`SceneLoader`)

- `LoadScreen(sceneName)`: если активна тяжёлая сцена — начать выгрузку; затем
  `LoadSceneAsync(sceneName, Additive)`; назначить загруженную сцену активной (для света и
  инстанцирования); на время async-промежутка показать индикатор загрузки в общем UI.
- Выгрузка через `UnloadSceneAsync` освобождает память 3D/видео/эффектов.
- Защита от двойной загрузки и обработка «гонок» при быстрой навигации.

### Разбивка UXML

`MikeyApp.uxml` разбивается через `<ui:Template src=...>` + `<ui:Instance template=...>`:
монолит становится тонким композиционным корнем, каждый экран — отдельный файл в
`Assets/UI/Screens/*.uxml`. Это убирает merge-конфликты и размер монолита.

### Структура папок (целевая)

```
Assets/
  Scenes/
    App.unity                          (постоянный бутстрап)
    Screens/
      Title.unity  Intro.unity  CameraTest.unity  Practice.unity  Map.unity
  UI/
    Screens/*.uxml                     (пер-экранные шаблоны)
    MikeyApp.uxml                      (тонкий композиционный корень)
  State/
    PlayerProfileState.cs + .asset
    ProgressionState.cs + .asset
  Navigation/
    SceneLoader.cs
    ScreenRoute.cs                     (реестр screenId → тип)
```

## Стратегия тестирования

- **Логика роутинга** (panel vs scene) — чистая, юнит-тестится без загрузки сцен.
- `SceneWiringTests` расширяется: App-сцена содержит `SceneLoader` + `ScreenManager` +
  ссылки на стейт; каждая тяжёлая сцена присутствует в Build Settings и содержит ожидаемый
  корневой маркер.
- **Аддитивная загрузка/выгрузка** — PlayMode-тесты (загрузка, активная сцена, выгрузка
  и освобождение).
- Существующие UXML-тесты адаптируются к пер-файловой разбивке.
- Зелёные тесты на каждом инкрементальном шаге.

## План миграции (фундамент + 1 экран)

Каждый шаг сохраняет приложение запускаемым и тесты зелёными.

1. **Фундамент-каркас.** Создать `App.unity` из текущего `SampleScene` (поведение не
   меняется; те же тесты проходят). Добавить в Build Settings.
2. **Роутер.** Добавить `SceneLoader` + реестр `ScreenRoute`, где пока **все** экраны
   помечены как `Panel` → поведение идентично текущему. `ScreenManager` маршрутизирует
   через реестр.
3. **Разбивка UXML** на пер-экранные файлы через Template/Instance; UXML-тесты обновить.
4. **Первый тяжёлый экран — `practice`** (у него уже чистый контроллер и понятный
   жизненный цикл): создать `Scenes/Screens/Practice.unity` с 3D-контентом за HUD; пометить
   `practice` как `Scene` в реестре; HUD остаётся в общем документе; добавить PlayMode-тест
   на загрузку/выгрузку. Это доказательство паттерна.

Последующие экраны (`camTest`, `title`, `intro`, `map`) выносятся тем же приёмом по одному.

## Риски и митигации

- **Настройка URP camera stacking** в каждой тяжёлой сцене → общий префаб камеры.
- **Редакторный воркфлоу:** разработчики открывают App + аддитивную сцену вместе →
  задокументировать editor-хелпер автозагрузки.
- **Активная сцена** для света/инстанцирования → выставляется `SceneLoader` при загрузке.
- **Гонки навигации** при быстрых переключениях → защита в `SceneLoader` (in-flight guard).

## Вне рамок (не делаем сейчас)

- Addressables / асинхронная стриминг-загрузка ассетов (можно добавить позже, если память
  всё равно станет узким местом).
- Полный перенос всех 10 экранов за один заход.
- Перенос лёгких экранов в отдельные сцены (они остаются панелями намеренно).
