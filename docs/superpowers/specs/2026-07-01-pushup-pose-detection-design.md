# Pose-детекция и анализ отжиманий: нативный MediaPipe + мост в Unity

**Дата:** 2026-07-01
**Статус:** одобрено к реализации (дизайн)
**Тема:** первое реальное упражнение (Gym reps → push-up): счёт повторений и оценка правильности
через on-device pose-детекцию. Фиксирует, **как** pose-движок подключается к Unity-проекту.

## Контекст и правка исходного ТЗ

Исходное ТЗ (PDF §6) предполагало **Native Android (Kotlin), CameraX + on-device pose**. Но
фактический репозиторий — это **Unity 6.3 приложение** (весь фронтенд на C#/UI Toolkit,
навигация через `ScreenManager`/`IScreenNavigator`). Возникла развилка из трёх вариантов:

1. **Чисто Unity** — pose-модель (MoveNet/BlazePose ONNX) через `com.unity.ai.inference`
   (Unity Inference Engine, уже в пакетах). Плюс: запуск в Editor. Минус: MoveNet 2D, точность
   ниже BlazePose; для прод-качества формы слабее.
2. **Чисто нативный Android** — отказаться от Unity для тренировочного экрана. Ломает
   существующую архитектуру экранов и HUD.
3. **Unity-приложение + нативный Kotlin/MediaPipe плагин (выбрано, вариант A).** ⭐

**Решение:** приоритет — прод-уровень, максимальная точность и real-time без лагов (это не ради
удобства тестов). Поэтому pose-инференс — официальный **MediaPipe Tasks Pose Landmarker**
(BlazePose, 33 3D-точки, GPU delegate, LIVE_STREAM), запакованный в нативный Kotlin-плагин, а
Unity остаётся слоем игры/HUD. Sentis/MoveNet отклонён из-за 2D и меньшей точности; чисто
нативный путь — из-за слома архитектуры.

Почему MediaPipe (проверено на 2026): это эталонный on-device real-time pose-стек Google —
30+ fps на среднем Android, трекинг между кадрами снижает латентность. OpenPose точнее, но
тяжёлый и не real-time на телефоне; RTMPose — серверный/multi-person; MovePose — ~11 fps и ниже
mAP.

## Ключевой принцип производительности

Перф-критичный путь (**камера + инференс**) остаётся полностью нативным. Кадры камеры **не**
пересекают JNI покадрово. Через мост в Unity уходят только:

- **landmark'и** — маленький payload (33 точки), в предвыделенном буфере, без GC-мусора на 30 fps;
- **GPU-текстура камеры** — через `SurfaceTexture` → `Texture2D.CreateExternalTexture` (хендл, не
  копия пикселей), чтобы Unity рисовал живое видео как фон под скелетом/HUD.

## Архитектура

### Нативный слой (Kotlin AAR → `Assets/Plugins/Android/`)

- `CameraX` — фронтальная камера, `ImageAnalysis`, режим потока.
- MediaPipe `PoseLandmarker` — GPU delegate, `RunningMode.LIVE_STREAM`, результат на нативном
  колбэке.
- Кадр камеры рендерится в `SurfaceTexture`; её OpenGL-текстура отдаётся в Unity (external
  texture) для показа. Тот же кадр идёт в MediaPipe на инференс — без копий в managed-память.
- Результат (33 × {x, y, z, visibility}, нормализованные координаты изображения) отправляется в
  Unity через `UnityPlayer.UnitySendMessage(target, "OnPoseResult", payload)`.

### Unity-слой (C#)

Новый bounded-context `Assets/Pose/` (asmdef `Mikey.Pose`):

- **`PoseLandmark` / `PoseLandmarkType`** — структура точки и индексы подмножества BlazePose,
  нужного для отжимания (плечи, локти, запястья, бёдра, лодыжки).
- **`PoseFrame`** — 33 точки + timestamp + флаг валидности (достаточная видимость ключевых точек).
- **`PoseMath`** — чистая геометрия (угол в суставе по трём точкам в 2D). Без UnityEngine —
  детерминизм и EditMode-тестируемость.
- **`PushUpRepCounter`** (чистый C#) — конечный автомат по углу локтя с гистерезисом:
  `Up (локоть ≥ ~160°) → Down (локоть ≤ ~90°) → Up = +1 повтор`. Порог «низа» — это и есть
  gate глубины.
- **`PushUpFormEvaluator`** (чистый C#) — покадровые проверки формы:
  - **линия тела**: угол плечо–таз–лодыжка ≈ 180°; провис таза или «домик» → cue;
  - **глубина**: достигнут ли порог низа в нижней точке (иначе shallow/no-rep);
  - **разведение локтей** (опц.), **темп** (опц.).
  → `FormStatus` (`Ready`/`Adjust`/`Good` + проблемные) и **один приоритетный cue** (§3.3).
- **`PushUpAnalyzer`** — композиция counter + evaluator; прод-замена мок-`CameraTestRepModel`.
  Держит текущее `Reps`, `FormStatus`, `Cue`; повтор засчитывается «чистым» только при пройденных
  глубине + линии тела (§4.2: shallow → no-rep).
- **`PoseBridge`** (MonoBehaviour) — JNI старт/стоп нативной сессии; приём `OnPoseResult`, парс в
  `PoseFrame`, подача в `PushUpAnalyzer`, проброс external-texture в материал фона; события для HUD.

### HUD

Переиспользуем существующий экран `camTest` (`Assets/UI/CameraTest/`): реальные `Reps` и
`FormStatus` из `PushUpAnalyzer` заменяют мок-инкремент в `CameraTestController`
(`camera-rep-count`, `camera-form-pill`, cue-лейбл). Добавляем рендер скелета (jade/ember по §4) и
фон-текстуру камеры.

## Поток данных

```
CameraX кадр
  → MediaPipe PoseLandmarker (native, GPU)         ── инференс
  → SurfaceTexture (external texture) ── в Unity ──→ фон камеры в HUD
  → landmarks → UnitySendMessage → PoseBridge
        → PoseFrame → PushUpAnalyzer (RepCounter + FormEvaluator)
              → HUD: счёт повторений, пилюля формы, приоритетный cue, скелет
```

## Критерии формы отжимания (стандартная биомеханика)

Пороги — конфиг, не хардкод; уточняются по эталонному видео/съёмке.

| Проверка | Метрика | Порог (старт) | Cue при нарушении |
|---|---|---|---|
| Повтор (низ) | угол локтя | ≤ ~90° | «Ниже» (если не дошёл) |
| Повтор (верх/локаут) | угол локтя | ≥ ~160° | — |
| Линия тела — провис | плечо–таз–лодыжка | < ~165° (таз низко) | «Выпрями спину» |
| Линия тела — «домик» | плечо–таз–лодыжка | > ~195° (таз высоко) | «Опусти таз» |
| Разведение локтей (опц.) | плечо–локоть отн. корпуса | > порога | «Локти ближе» |

Съёмка предполагается сбоку (профиль) — самый надёжный ракурс для отжиманий; скоринг по 2D
(x, y) устойчивее, чем по шумному одиночному z.

## Обработка ошибок и деградация (NFR §)

- Низкая уверенность / тело не в кадре → `FormStatus.Ready` («Align in frame»), счёт на паузе,
  подсказка по кадрированию (существующее состояние Ready).
- Отказ в доступе к камере → graceful-состояние.
- Пропуски точек → удержать последнее состояние кратко, повтор не засчитывать.
- Кадры обрабатываются on-device, не выгружаются (privacy §NFR).

## Тестирование и dev-харнесс

- **Чистая логика** (`PushUpRepCounter`, `PushUpFormEvaluator`, `PoseMath`): EditMode-тесты на
  синтетических потоках точек — чистый повтор, shallow-повтор, повтор с провисом таза → проверяем
  счёт и cue. Зеркалит существующие `CameraTestRepModelTests`.
- **Dev-сцена `ExerciseSandbox`** (создаётся пунктом меню *Mikey/Dev*): отдельная сцена вне
  игрового флоу, «нажал Play → тестишь». Два экрана: **выбор упражнения** (список из
  `ExerciseCatalog`) → **камера** запускается после выбора. В **Editor** источник —
  `SimulatedPoseSource` (веб-камера ноутбука не используется: прод-путь нативный Android,
  real-time инференс в Windows-редакторе не запускается). На **Android-устройстве** — реальный
  MediaPipe.

**Обобщение под несколько упражнений:** `IExerciseAnalyzer` (общий контракт: reps, cue,
`ExerciseFormState`) + реестр `ExerciseCatalog`. `PushUpAnalyzer` его реализует; `PoseController`
и HUD агностичны к упражнению. Добавить новое упражнение/технику = одна запись в каталоге →
оно само появляется в выборе и работает через тот же пайплайн.
- **On-device smoke**: сборка APK, реальные отжимания, счёт vs ручной подсчёт + корректность cue.

iOS вне области: текущий плагин — Android AAR (Kotlin); для iOS нужен отдельный нативный плагин.
